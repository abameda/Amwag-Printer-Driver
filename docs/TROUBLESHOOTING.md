# AMWAG Printer Setup — troubleshooting

## Where to look first

1. **The report.** On any result screen: *Save report…* or *Copy report*. Silent runs write it to `--report` or
   `%ProgramData%\AMWAG\PrinterSetup\Reports`. The report lists the platform, spooler, every printer device, queue,
   port and relevant driver, the ticket form, what was detected and why, the plan, every action's outcome, every
   verification check (expected vs actual) and all findings with their codes.
2. **The logs** (JSON lines, one event per line, kept 60 days):
   * the employee's window: `%LOCALAPPDATA%\AMWAG\PrinterSetup\Logs` (*Open log folder*);
   * the elevated worker and silent/IT runs: `%ProgramData%\AMWAG\PrinterSetup\Logs`.
   All processes of one run share the same session id (in the file name and every line).
3. **Diagnostics mode** never changes anything and needs no administrator rights:
   `"AMWAG Printer Setup.exe" --mode diagnostics` (or `--silent --mode diagnostics --report C:\Temp\diag.txt`).

## Findings and what to do

| Code | Meaning | What to do |
|---|---|---|
| `DimensionsUnconfirmed` | The configuration's ticket size is not confirmed by IT; Setup/Repair are blocked. | Measure the stock, set `ticket.dimensionsConfirmed`, `confirmedBy`, `confirmedOn` (DEPLOYMENT.md §2). |
| `ConfigurationInvalid` | `amwag-printer-config.json` or `branch.json` failed validation. | The error list names each field. Fix and re-run. |
| `SpoolerNotRunning` / `SpoolerDisabled` / `SpoolerUnavailable` | The Print Spooler is stopped, disabled or not answering. | The tool starts a stopped spooler (one UAC prompt). A *disabled* spooler is a policy decision: re-enable it (`services.msc`) or ask the owner of the policy. |
| `ProtectedPrintModeEnabled` | Windows protected print mode blocks third-party drivers. | Turn it off (Settings → Bluetooth & devices → Printers & scanners → Printer preferences) unless policy enforces it; then reinstall. |

Network: check that the printer at that address is on and is the ticket printer, enter its IP address, or correct `printerAddress` in `branch.json`. With nothing usable at the configured address, every mode shows *Ticket printer not found at its address* with the headline *No ticket printer at this address* naming the address; no other printer is used in its place, and the window offers *Try again*, but no *Run Setup* and no Repair. When the error names a queue that is left unchanged (`QueueLeftUnchanged`: a pooled, LPR or IPP queue that prints to the printer at that address), fix that queue first: Setup, Repair and Diagnostics show *The ticket printer cannot be set up automatically* with the headline *Printer entry left unchanged*, which names the queue and the address (the technical details give the reason), and the step reads *Detecting printer: Printer not set up automatically*. When the employee did not confirm the model (answered *No*, or chose no model for a printer that does not report one), Setup and Repair end *The printer was not changed* / *Its model was not confirmed, so nothing was changed.* with the headline *Printer model not confirmed*, and the step reads *Printer found; model not confirmed*; *Try again* asks again. Repair never adds a printer to Windows, and nothing was changed in any of its ends: when the ticket printer has no queue yet, it ends *Nothing to repair yet* (headline *Printer not set up yet*) with *Run Setup*; when supported printers were found but none has a queue, *Nothing to repair yet* with *None of the printers found has been added to Windows yet …* and the headline *Printers not set up yet* (step *Printers found, none set up yet*), with *Run Setup*; when it finds no supported printer at all, *No ticket printer found* with *Run Setup*. In the window, Repair does not ask to confirm the model of a printer that has no queue: it ends *Nothing to repair yet*, and *Run Setup* asks the question once. |
| `MultipleSupportedPrinters` | More than one supported printer; or a single printer that is not certain to be the ticket printer (another model than `modelId`/`--model`, next to a queue that could not be matched to its printer or cannot be configured, or next to a queue the limit of network probes left unchecked), which is offered instead of set up without asking. | Choose on screen; for silent runs use `--address`/`--model` or `branch.json` (silent Setup and Repair otherwise stop with exit 4, and the `Cancelled` warning says which of them can decide). Repair changes only the ticket printer and lists the others as not changed; Diagnostics warns when it cannot tell which printer is the ticket printer and names each one, including those whose model must be confirmed first (with their switches); a `modelId` that is already set and does not tell them apart is not advised again. Two connected USB printers of the same model cannot be told apart by `--address`/`--model`: run interactively or disconnect the other printer. Next to a rejected queue whose printer may be of the same model as the only printer, or of `modelId` (the queue uses that model's driver, a probe of a host it prints to suggests that model, or its driver names no single model and no printer at its hosts answered SNMP), no switch tells a USB printer apart either: check the printer of that queue (delete the queue if that printer is gone), or choose on screen; a network printer is named with `printerAddress`/`--address`. Next to a queue the limit of network probes left unchecked (`NetworkIdentityUnavailable`), `modelId`/`--model` chooses none: name the host of the ticket queue with `printerAddress`/`--address` (the host of the queue that was found sets up that queue, which is right only if it is the ticket queue), choose the ticket printer in Setup, or raise `connection.maxNetworkProbes`. Diagnostics also warns when the printer at the configured address has several queues and none is known to be the ticket queue (choose it in Setup, set `--address` to the host of the ticket queue, or delete the queue that is not used), or one queue on another host while other queues were not checked (choose it in Setup, or set `--address` to the host of the ticket queue), and Repair when the queue of an unplugged earlier USB unit alone has the ticket paper (run Setup once, or delete that queue). In the window, Setup asks for the ticket printer's address when none of the printers offered is chosen; Repair then ends *Repair was stopped* and changes nothing. |
| `ProbableMatchRequiresConfirmation` | The network printer names a model but its exact identity could not be read, or it answers without naming a model. | Confirm only if the model is right (check the printer's label/status page); Setup and Repair both ask, and with several such printers the employee first chooses one (Repair asks only about the one whose queue has the ticket paper, when one has). Silent runs stop with exit 4: re-run with `--address <ip> --model <id> --confirm-model` (the finding names them; with several such printers each gets its own finding). Diagnostics reports it as not ready (exit 2), also for the printer whose queue has the ticket paper that Repair would ask about. When the employee answers *No* (or cancels the model choice) for the printer at the configured address, no other printer is used instead: the window asks for the right address, and without one nothing is set up (exit 3). A printer that answers without naming its model is asked about only at a configured or entered address, or when it is another spelling of a printer that has another queue. |
| `NetworkIdentityUnavailable` | The printer answers on port 9100 but not to SNMP (window: *Printer model could not be read*). Also when the limit of network probes (`connection.maxNetworkProbes`) left a printer unchecked: a requested address ("… was not probed because the limit of network probes was reached."), or the host of an existing class-driver queue on one Standard TCP/IP port that no other probed spelling of a printer leads to ("Queue X on H was not checked because the limit of network probes was reached; it may be the ticket printer's queue."). Such a queue may be the ticket printer's, so a single printer next to it is offered instead of set up without asking (silent: exit 4). In the window both read *Printer not checked*: *A printer was not checked because the limit of network checks was reached, and it may be the ticket printer. Ask IT to raise the limit or to name the ticket printer's address.* This note and *Printer model could not be read* can both show. | Enable SNMP v1/v2c (community `public` or the configured one) on the printer, or confirm the model when asked (`--model --confirm-model` in silent runs). Not checked: raise `connection.maxNetworkProbes`, or name the ticket queue's host with `--address` or `printerAddress`. A silent run that stops for an unchecked queue (exit 4) names the queue of the printer that was found and the host that sets up that queue ("If 'A4 office' on printer12 is the ticket queue, name that host with printerAddress printer12 in branch.json or --address printer12, or choose it in Setup."; a USB printer: "Choose the ticket printer in Setup."), then names each unchecked queue with its host: "Queue(s) 'Tickets' on printer12.branch.local were not checked because the limit of network probes was reached, and one of them may be the ticket printer's: name the host of the ticket queue with --address or printerAddress, or raise connection.maxNetworkProbes in the configuration so that they are checked (see the NetworkIdentityUnavailable finding)." |
| `NetworkPrinterUnreachable` | No answer on the raw print port (9100). | Check the IP address, network, VLAN/firewall, and that the printer is on. |
| `IdentityConflict` | The device reports another supported model than its queue's driver; the queue is repaired to the device's model. | Check that the right printer is connected at that address. |
| `NetworkIdentityMismatch` | The device at the address names an unsupported model (IEEE 1284 MDL, Kyocera model name or device description), several models, or another manufacturer; its queues are not configured. Reported when one of its queues uses a supported model's driver or the address was configured or entered. A pool that is a USB printer's queue and also prints to such a device is named as staying the USB printer's queue ("Queue X stays the queue of the USB printer M (key) and also prints to this device."); only the device's other queues are said to be not configured. Also when a model confirmed by the employee or given with `--confirm-model` contradicts what the device reports (its exact or probable model, or a model its probes name): the employee may choose another printer; IT's model stops the run with nothing changed (exit 4), and the error names both models (also in Repair when the printer has no queue yet, and when every queue of the printer at `--address` contradicts it). In the window the result's headline is *Model does not match this printer*: it names the model given with `--model`, the address and the model the printer reports (or *another model*), the banner reads *The printer was not changed*, and *Try again* is not offered, because the window cannot change its switches: close the program and start it again with the correct `--address`/`--model`. | Check which printer is at that address and its model on the label or status page; correct `--address`/`--model`. A printer's administrator-assigned name is never used to identify it. |
| `UnsupportedPrinterDetected` | A TA/UTAX/Kyocera printer that is not in the configuration (information), or a USB printer whose IDs match several models (warning); it is not changed. | Only P-4030DN, P-4531DN, P-5032DN are supported (DEPLOYMENT.md §10 to add models). |
| `QueueLeftUnchanged` | A queue was not configured; its driver names a supported model, except for the class-driver queues below. As a warning: the device node on its USB port (also switched off) names an unsupported, several or another model, or another manufacturer's printer is connected there; a WSD queue is next to a connected TA/UTAX/Kyocera WSD printer of another or an unsupported model that no other WSD queue can belong to; the queues of one TCP/IP host have drivers of different models; or the queue is pooled over Standard TCP/IP ports or uses an LPR Port or Internet (IPP) port. In that last case it is never configured, and the printer it prints to is not set up automatically under any of its spellings: one warning per printer, and with that printer's address nothing is set up (silent: exit 3, and the `NoSupportedPrinterFound` error names the queue). A queue pooled over a USB port and TCP/IP ports stays the USB printer's queue and is configured for it; only the network printer at its TCP/IP ports is not set up automatically (with that printer's address: exit 3). Also as a warning: a queue with a class driver that is pooled over Standard TCP/IP ports, or a class-driver queue on an LPR or Internet Port that is already set up as the ticket printer's queue among the queues of the printer it prints to (ticket form, or the configured queue name), also when that printer has no other queue; the printer it prints to is not set up automatically (with its address: exit 3). Also as a warning: a queue already set up as the ticket printer (ticket form, or the configured queue name) that may be a TA printer's but leads to no printer the setup can configure: a queue whose driver names no single model (such as a class driver) on a WSD, LPR or Internet Port whose printer has no queue the setup configures, or a queue to a printer that does not answer or does not report its model ("Queue 'Tickets' uses driver '…', which names no single model, is already set up as the ticket printer and prints through port P, but it leads to no printer the setup can configure, so it is not configured, and no other printer is taken as the ticket printer without asking. …"; on a Standard TCP/IP port: "… and prints to H, whose printer does not report its model or does not answer, so it is not configured, …"); a queue of a device that reports another vendor or an unsupported model is not reported this way. As information: a queue on a port that names no printer's host (a local port redirected to a share, a TCP/IP port without a host, an LPR or Internet Port whose name gives no host, pooled ports none of which does); it is also a possible duplicate (`DuplicateQueues`) of a requested printer without a queue. As an error (a plan blocker, or a failed `CreateQueue` in the worker), a queue the setup does not configure for this printer already prints to the Standard TCP/IP port or the USB port a new queue would use, and nothing is changed (exit 8). On a USB port this happens when a stale `modelId` (or an operator) picks an earlier unit whose port the connected unit's pool lists; correct `modelId`, then run Setup again. Without an address a queue named in one of these warnings may be the ticket printer's, so no other printer is set up without asking (silent: exit 4), and `modelId`/`--model` does not choose one either when that queue's printer may be of that model (its driver's model, a model a probe of its hosts suggests, or any model when its driver names none and no printer at its hosts answered SNMP). When such a queue is on the ticket paper, Repair does not take another queue on the ticket paper as the ticket printer's: it asks (silent: exit 4). | Connect or switch on the ticket printer and run again; un-pool the queue or put it on a single Standard TCP/IP port (an LPR or IPP queue: on a Standard TCP/IP port; a pool with a USB port only when the printer at its TCP/IP ports is the ticket printer); or give the host's queues one approved driver. A ticket queue that leads to no printer the setup can configure: on a Standard TCP/IP port, name that port's host with `printerAddress` (silent: `--address <host> --model <id> --confirm-model`; switch the printer on first if it does not answer), and the queue itself is configured; on a WSD, LPR or IPP port, put it on a Standard TCP/IP port to its printer, or delete it and name the printer with `printerAddress`, then run the setup again. Otherwise delete the queue, or choose on screen (silent: `--address`/`--model`). |
| `DeviceNotConnected` | A USB printer (or its queue) is not connected now. An unplugged USB printer of the same model as a connected one (its device node, or a USB queue whose device is gone) is treated as an earlier unit (replaced or a loaner): it is left out of the choice, of Repair and of Diagnostics and reported as information. Repair still asks (silent: exit 4) when only the earlier unit's queue is already set up for tickets, also when the connected unit has no queue yet, because it may be a switched-off ticket printer next to an identical office printer; Diagnostics then checks both, and the note that the unit is left out is not shown. Otherwise it stays a warning and a choice, so a switched-off ticket printer is never replaced by another printer. An earlier unit's node that has its own queue is reported as "it and its queue X are left out because a USB printer of the same model is connected", followed by any pool over its port that the connected unit uses and that is not left out (Data `queue` = X, `keptQueue` = the pool). "Only that device node is left out" appears when the node has no queue of its own, or its queue is that pool. An earlier unit's node never claims a queue that a connected printer on the queue's ports uses, or whose driver names another node's model. | Connect/power the printer; configuration is still verified. An old unit's node can be removed in Device Manager (*View → Show hidden devices*). While the old unit's queue has the ticket paper, Repair keeps asking: run Setup once (it sets up the connected unit as the ticket printer; when printers whose model must be confirmed are found as well, Setup offers them next to it, so choose the ticket printer in Setup's window, or set up a network one silently with its switches), or delete the old queue if that printer is gone. |

## Common situations

* **The test ticket prints on A4 or is scaled.** The printer's MP tray paper size on the operation panel must be
  *Custom* (Menu → Paper Settings → MP Tray Set. → Paper Size). Then run Repair and print the test ticket again.
* **The test ticket is right but real tickets are not.** The ticket software overrides the defaults — run
  *Check ticket software* and fix its page setup.
* **Windows created a queue named "… (Copy 1)" or with "Microsoft IPP Class Driver".** Since July 2026 Windows prefers
  its IPP class driver for some printers. For a USB queue, or a Standard TCP/IP queue whose printer reports its model
  (SNMP), run Repair: it switches the queue to the approved driver. When the port has two queues (the queue and its
  copy) and neither is set up for tickets yet, the run configures one, chosen by its driver and name, and ends ready
  with warnings (*Printer added more than once*): check which queue employees print to. A WSD queue, or a queue on an
  IPP port, on a class driver cannot be linked to its printer and is not changed: Repair finds no queue to repair, and
  Setup with the printer's address adds a Standard TCP/IP queue next to it and ends ready with warnings (silent:
  exit 1): the window shows *Another printer entry may print to this printer*, naming the class-driver queue (and any
  other entry that may print to the printer, such as an office printer's WSD entry: keep that one), and the
  report keeps the possible-duplicate warning (`DuplicateQueues`). Make sure the ticket software prints to the new
  queue, and delete the class-driver queue afterwards if employees should use only the new one. When the queue on the
  IPP port is already the ticket queue (it uses the `AMWAG Ticket` form, or has the configured queue name), Setup with
  the printer's address sets up nothing (`QueueLeftUnchanged`, exit 3): put that queue on a Standard TCP/IP port, or
  delete it, then run Setup again.
* **"Another run is applying changes".** A second copy (or an IT deployment) is configuring the PC. While it waits the
  window shows *Waiting for another AMWAG Printer Setup run to finish…*; if the lock stays busy, *Another setup is
  running* (`ApplyLockBusy`): nothing was changed, the steps say *Not started*, and the run ends not ready (exit 2).
  Try again in a few minutes.
* **The window says the configuration changed and to close the program and start it again.** IT changed
  `amwag-printer-config.json` or `branch.json` while the window was open, or the administrator step cannot load it any
  more (`ConfigurationChanged`). Nothing was changed. Close and restart; if the program then reports an invalid
  configuration, fix the file.
* **Closing the window during setup.** A step running with administrator rights (for example a driver installation)
  finishes first; later steps are not started. The window shows *Stopping after the current step…*, waits (up to about
  6 minutes), reads the printer back, then closes. Clicking X again does not close it sooner. When Windows shuts down,
  a window started as administrator (it runs the steps itself) asks Windows to wait until the running step has
  finished. Run the tool again to finish.
* **Repair after a Setup or test print.** The Repair buttons repair the printer of the result by its identity at the
  time Repair runs. If the printer now reports another model than its queue's driver (it was asleep during Setup),
  Repair switches the queue to that model's approved driver. A model chosen by the employee or asserted by IT stays.
  The result offers Repair only where Repair can change something, a printer with a queue. Setup can end before the
  queue is added (the driver could not be obtained or installed): the result then says *The printer has not been added
  to Windows. Solve the problem shown below, then try again.* and offers *Try again*, not Repair. Diagnostics of a
  printer that was never set up says *The printer has not been added to Windows yet. Run Setup to set it up.* and offers
  no Repair, nor does Diagnostics that found no printer. When Diagnostics does not know which printer is the ticket
  printer (several printers, or a printer whose model must be confirmed), it offers Repair only when one of those
  printers has a queue of its own. Otherwise it says *The printer has not been added to Windows yet. Run Setup to set it
  up.* (several printers: *The printers found have not been added to Windows yet. Run Setup to set up the ticket
  printer.*). Diagnostics on a computer that cannot be set up as it is (Print Spooler disabled or not running, protected
  print mode, unsupported Windows or processor, invalid configuration) offers no Repair, because Repair would stop the
  same way. A result that is not ready and offers no Repair never mentions Repair (*Some settings could not be
  confirmed. Solve the problem shown below, then try again.*). After Repair the result speaks of Repair: *Repair was
  stopped* (for example when no printer was chosen), *Repair cannot continue*, *Repair did not finish*.
* **The log says the configuration file "is not used because …; the configuration built into the program is used
  instead".** The file is in a folder a standard user can change (USB stick, Desktop, Downloads, or a share where
  employees can write), so no run trusts it. Run the tool from a folder only administrators can change, or rebuild with
  the edited configuration (DEPLOYMENT.md §1 and §3). The reason names the owner, or the account that can change the
  file or folder.
* **The helper's log shows `worker.pipe.unavailable` or `worker.cancelled` with exit code 9.** The elevated helper
  could not reach the window, or the window was closed: it changed nothing, or stopped after the step that was running.
  `worker.pipe.foreign_server`: the pipe did not belong to the window that started the helper; `worker.pipe.stalled`:
  the window did not read for 30 s; in both cases nothing was changed, or the helper stopped after the running step.
  `elevation.connect.failed` "ended before it connected": the helper changed nothing; its own log says why
  (`worker.not-elevated`, `app.arguments.invalid`, `worker.pipe.unavailable`).
* **The report's apply results say `NOT APPLIED (refused: <code>)`.** The administrator step changed nothing (another
  run was applying changes, the printer was not found again, the configuration changed, or a blocker); the finding
  below names it. The state shown is read back from the system, except when the refusal blocks the run (the
  configuration changed, or the administrator step found a blocker): nothing was changed, and the report shows the
  state detected before the step.
* **Setup cannot continue — Some changes were made, but the setup cannot finish.** A blocker was found after the
  administrator steps changed something, for example the paper range of the driver just installed does not include the
  ticket size (`DriverDoesNotListForm`, `TicketSizeOutsideDriverRange`; exit 8). The driver, queue or form may already be
  installed; the details show the printer as it is now. Fix the cause shown, then run Repair. Starting the Print Spooler
  does not count as a change (the helper does it before the printer is detected): a run that only started the spooler
  and then found a blocker says *A required condition is not met. Nothing was changed.*
* **The result screen shows fewer warnings than the report.** Once actions ran, it shows only what still holds at the
  end; what the first check found before the changes (for example *Driver not installed* or *Unplug the USB cable*
  before a successful install) is left out, and the report keeps every finding. A warning about the run's own change
  stays, and the run ends ready with warnings: a queue added next to another queue that may print to the same printer
  (*Another printer entry may print to this printer*), or a queue chosen among queues of the printer that could not be
  told apart (*Printer added more than once*). At most four warnings are shown; `DriverPackageIntegrityFailed`,
  `DriverSignatureInvalid` and `ConfigurationInvalid` always come first, also as the headline among warnings of a run
  that is not ready. A failed run is then headlined by the failure that ended it (the elevated helper could not start
  or gave no result: *Administrator step failed* or *Something went wrong*, with the helper's error in the technical
  details). In Diagnostics the headline and the warnings are about the ticket printer
  when it is known; the other printers checked are listed in the details and keep their findings in the report. In the
  details list each printer checked starts with its name at the reading edge, and its checks are indented under it.
  Screen readers hear each check with its values, for example "Print Spooler service: Passed. Expected: Running   Found:
  Running". A blocked Diagnostics result always says *Nothing was changed*, also when the report could not be created.
* **An apply step reads *Not started; nothing was changed*.** It never began: approval was declined, the helper did not
  start or refused (another run, the printer was not found again, the configuration changed, a blocker), or every
  action of the step was skipped after an earlier one failed. *Not finished: the setup was stopped* means the window was
  closed during the run; *Not changed: Diagnostics only checks* is Diagnostics. *Not finished: another step failed*
  means the step began but could not finish because an action of the other apply step failed (for example the ticket
  paper size was created, the driver install failed, and the ticket defaults were never written). *Not reached* (any
  step, *Verification* included) means the run ended before that step. During Setup and Repair *Checking driver* reads
  *Driver will be installed* (or *updated*) for a missing (or outdated) driver. At the end, *Checking driver* reads
  *Driver is ready* when the read-back finds the approved driver, and *Driver not installed* (or *Driver not updated*)
  when it finds the driver missing. When the read-back could not find the printer again, the run's own install action
  decides instead (succeeded or already installed: *Driver is ready*; failed: *Driver not installed*). A run that ended
  before anything was applied still reads *Driver not installed* (approval declined, helper not started). *Driver state
  not confirmed* means neither the read-back nor an install action says it.
* **The ticket printer is offered instead of set up, next to a class-driver pool to other printers.** The IP addresses
  that pooled, LPR and IPP queues print to are not probed (only their host names are). A class-driver pool to another
  vendor's printers on IP addresses is therefore reported as `QueueLeftUnchanged` and counts as a rejected queue: the
  ticket printer is then offered rather than chosen automatically (silent: exit 4), also with `modelId`, because the
  pool's printers may be of any model. Deleting the unused pool, or naming the ticket printer with `printerAddress`,
  avoids the question.
* **Setup is blocked (exit 8) after a USB ticket printer was replaced by another model, but Repair says *Nothing to
  repair yet*.** `modelId` still names the old model, and the new unit's queue is pooled over both units' USB ports:
  Setup takes the earlier unit and adds no second queue on its port (`QueueLeftUnchanged`, exit 8), while Repair ends
  *Nothing to repair yet* with *Run Setup*, and Diagnostics also points to Setup. Repair and Diagnostics do not name the
  blocker themselves. Correct `modelId` (or remove it), then run Setup again.
* **Silent run exit codes** are listed in DEPLOYMENT.md §7.
